Volume II · Building For Agents

The Context Era

Eleven sources converge on one craft: as software grows agents that act on their own, the work moves from writing prompts to architecting the context — instructions, memory, retrieval, and tools — that an autonomous worker reasons inside. NN/G ports information architecture to that "context ecosystem"; Spotify and LinkedIn ground their assistants in expert and domain knowledge; IBM names the discipline; and the economics arrive with the bill — re-sent context that makes token spend grow parabolically.

11 sources · 2 diagrams · ~21 min read Distilled from NotebookLM · personal reading log

§1 · OrientationFrom prototype to profession

Today's eleven sources document one transition: the move from prototyping generative AI to engineering it. The throughline is that an agent is only as good as the world you build around it. When a model merely answered, the unit of work was the prompt. When a model acts — running multi-step tasks, calling tools, carrying state across turns — the unit of work becomes the context: the instructions, the memory, the retrieval scope, and the tools it can reach. NN/G frames this as information architecture for a "context ecosystem." Spotify and LinkedIn show what grounding that ecosystem in real expertise costs and earns. IBM gives the discipline a name. And the cost pieces deliver the catch — done carelessly, the context you assemble each turn gets re-sent so often that spend curves bend the wrong way.

The agentic-cost thread has run through this archive — the June 10 issue tallied where token spend actually goes; today asks the harder structural question underneath it: is parabolic token consumption an accident of sloppy plumbing, or the price of admission for agents that remember?

Six agreements across today's sources

  1. Context is the new unit of engineering. Across NN/G, IBM, Spotify, and LinkedIn, the work has moved off the model call and onto the environment — instructions, memory, retrieval, and tools — that the agent reasons inside. Prompting is a subset of it now, not the whole job.
  2. Information architecture is the right lens. The same discipline that organized websites — labeling, hierarchy, findability — is what keeps an agent's context legible. Disorder there is not cosmetic; it degrades the model.
  3. "Context rot" is real and it is structural. More context is not better context. Past a point, excess and disorganized material actively lowers output quality — the failure mode every source is implicitly designing against.
  4. Grounding beats raw capability at the enterprise edge. Spotify's domain "teacher" layer and LinkedIn's semantic retrieval both bet that piping in expert and domain knowledge matters more than a bigger model. Retrieval and ranking are the product.
  5. Agentic scale has a money problem. The "re-sent context" problem — re-transmitting accumulated state every step — makes token consumption grow parabolically, not linearly. Reliability and cost are now the same design conversation.
  6. Humans own the essential complexity. AI absorbs the accidental kind — boilerplate, glue, scaffolding — but conceptual integrity, design judgment, and alignment to a user's mental model stay human. That division is the recurring boundary line.

§2 · StructureInformation architecture for the context ecosystem

The day's most structural source is NN/G's framing of context architecture: the claim that designing an agent's context is the same problem as designing a website's information architecture, just relocated from pages to prompts. An agent reasons over a bundle — system instructions, working memory, retrieved documents, tool definitions, conversation history — and that bundle has structure whether you design it or not. Labeling, hierarchy, scope, and findability are not website-era concerns left behind; they are exactly what determines whether the model can locate the right fact at the moment it acts. IBM's What is Agentic Engineering? arrives at the same place from the engineering side: the new discipline is less about model selection than about assembling a reliable operating environment around the model.

The synthesis neither source states alone: the agent's context window is a designed information space, and the failure mode is the same one IA always fought — too much, badly organized, so nothing is findable. NN/G calls the degradation "context rot." The reframe that matters is that this rot is not a model limitation to be waited out; it is an architecture problem, which means it is yours to fix. The lever is not a bigger window but a better-organized one.

Figure 1 · The context ecosystem read as a stack from durable to volatile. The bands you set once and design carefully (bottom) are cheap and stable; the bands that accumulate and re-send every step (top) are where both context rot and the token bill come from — which is why organizing the stack is an engineering decision, not a writing one.

§3 · GroundingSpotify and LinkedIn: the expert in the loop

Two enterprise sources show what context architecture looks like in production, and they agree on the unglamorous answer: the moat is the retrieval layer, not the model. Spotify's account of the data assistant behind its analytics describes encoding a domain expert — building a "teacher" layer that injects how Spotify's own analysts define metrics, name tables, and reason about data, so the assistant answers like a colleague rather than a stranger reading schemas cold. LinkedIn's piece on its Hiring Assistant is the same bet expressed as semantic search at scale: the engineering effort goes into retrieval and ranking — surfacing the right candidates and the right context, in the right order — because a hiring agent that retrieves badly is worse than useless, it is confidently wrong.

The synthesis across the two, present in neither alone: at enterprise scale the differentiator is grounding, and grounding is a human-knowledge pipeline, not a model upgrade. Both companies are pouring effort into capturing what their experts know and feeding it into the agent's context — Spotify as a teaching layer, LinkedIn as a ranking layer. The generic frontier model is a commodity input to both; the proprietary, expensive, defensible part is the domain knowledge piped in around it. That is the enterprise mirror of NN/G's argument: the value is in how the context is organized and sourced, not in the engine consuming it.

§4 · Naming itAgentic engineering, defined

IBM's What is Agentic Engineering? does the quiet work of naming the discipline the other sources are practicing: the design and operation of systems where AI agents plan and execute multi-step tasks with some autonomy. The piece's value is less the definition than the shift in posture it implies — from "write a good prompt and check the answer" to "build a system that reasons, acts, observes, and corrects across many steps, and instrument it so you can trust it." Reliability, observability, and guardrails become first-class concerns, because an autonomous worker that errs at step three of twelve has already acted on the error by step four.

The synthesis worth keeping: "agentic engineering" is the umbrella under which today's other pieces are specialties. Context architecture (NN/G) is its information-design wing; Spotify's teacher layer and LinkedIn's retrieval are its grounding wing; the cost pieces are its economics wing. Naming the field matters because it tells you what to hire for and what to measure — and that the measure is no longer answer quality on a single turn but task completion across a trajectory.

CounterThe risk in naming a discipline this early is premature ceremony. "Agentic engineering" can ossify into process theater — frameworks, certifications, and ritual scaffolding — before the field knows which practices actually move reliability. The honest version of the term is descriptive, not prescriptive: it points at a real shift in the unit of work, but anyone selling you the canonical methodology for it in mid-2026 is ahead of the evidence.

§5 · EconomicsThe re-sent context problem

The day's hardest-nosed source is Managing Agentic AI Costs at Scale, and its central observation reframes everything above as a budget problem. The mechanism is the re-sent context problem: at each step of a multi-step task, an agent typically re-transmits its accumulated context — the prior turns, the tool outputs, the retrieved documents — back to the model so it can reason about the next move. As the task lengthens, the context carried forward grows, and because it is re-sent every step, total token consumption does not rise linearly with task length; it rises closer to quadratically. A task twice as long can cost roughly four times as much. The agentic loop that makes the technology powerful is the same loop that makes it expensive.

The synthesis that ties this back to §2: context rot and the token bill are the same phenomenon priced two ways. Bloated, badly organized context degrades the model's output (NN/G's quality cost) and inflates the per-step payload (the dollar cost) simultaneously. This is why the discipline's two obsessions — reliability and cost — are not separate tracks. The lever for both is the same: keep the carried context tight, compressed, and curated. Good information architecture is, quite literally, a cost-control measure.

The agentic-cost thread is a running one in this archive — the June 10 issue tallied where token spend actually goes inside a workflow. Today's piece supplies the structural why beneath that tally: it is the re-sent-context loop, not any single wasteful call, that bends the curve.

§6 · The long viewWhat stays human: the mythical agent-month

Wes McKinney's The Mythical Agent-Month — a deliberate echo of Brooks's The Mythical Man-Month — is the day's stretch piece, and it supplies the boundary the rest of the sources circle. Brooks's old distinction between essential and accidental complexity is the right tool for the agentic era. Agents are extraordinary at the accidental kind: the boilerplate, the glue code, the mechanical translation between layers, the scaffolding that has no inherent conceptual content. They are far weaker at the essential kind: deciding what the system should be, holding conceptual integrity across a large design, and keeping the whole aligned to a user's mental model. Throwing more agents at a problem does not collapse essential complexity any more than throwing more programmers did — Brooks's warning survives the substitution.

Read the rest of the day through this lens and the sources stop competing and start composing. Two adjacent essays in the set — The Architectures of AI-Native SaaS and The Inverted Market: How AI is Reshaping Software Consultancy — describe the same boundary from the market's side. AI-native SaaS is being rebuilt around agents that act inside the product rather than features a human drives; the consultancy market is inverting because the accidental-complexity work that filled billable hours is collapsing in cost, leaving the essential-complexity work — judgment, integration, conceptual design — as the scarce thing worth paying for. Two short signals round out the day: Ishaan Sehgal and Satya Nadella on X both gesture at the same agentic-platform turn from the practitioner and the platform-CEO vantage points. And as a reminder that the substrate keeps moving underneath all of this, Python 3.15 ships practical performance upgrades — the unglamorous tooling progress that quietly raises the floor.

The synthesis, stated by none of them directly: the entire stack of today's pieces is a map of where the human line falls. NN/G, IBM, Spotify, and LinkedIn are all building machinery to hand agents more of the accidental complexity reliably and cheaply; McKinney, the SaaS essay, and the consultancy essay are all describing what is left over when that machinery works — and it is the same residue every time. Conceptual integrity does not parallelize. The agent-month is mythical for the same reason the man-month was.

CounterThe comfortable reading — "essential complexity is a permanent human moat" — assumes the essential/accidental line holds still. It may not. Much of what looks essential today (system design, conceptual integrity) is essential partly because current agents are bad at long-horizon coherence, exactly the axis the grounding and context work in §§2–3 is built to improve. McKinney's framing is the right starting tool, not a law of nature; the line it draws is a snapshot of a moving frontier, and betting a career on its current position is its own kind of myth.

§7 · Practical takeawaysIf you only do seven things this week

  1. Treat the context window as designed information space. Before adding to an agent's prompt, ask the IA questions: is this findable, is it labeled, does it belong at this layer? Apply Figure 1 — durable instructions at the base, volatile working state at the top — and review the structure, not just the wording.
  2. Audit your carried context for re-sent waste. Trace one real agent task and log the token payload per step. If it grows roughly quadratically with task length, you have the re-sent context problem, and compression — not a cheaper model — is your highest-leverage fix.
  3. Invest in retrieval and grounding before a model upgrade. Spotify and LinkedIn both bet that piping in expert and domain knowledge beats a bigger engine. Spend on the teacher layer and the ranker before you spend on the frontier tier.
  4. Design against context rot explicitly. More is not better. Set a budget for how much context a task may carry, prune aggressively between steps, and treat unbounded history as a bug rather than a convenience.
  5. Instrument for trajectories, not turns. An agentic system's quality metric is task completion across many steps, not answer quality on one. Add observability that shows you where in the trajectory things go wrong, because by the next step the error has already propagated.
  6. Hand agents the accidental complexity, keep the essential. Route boilerplate, glue, and mechanical translation to agents; reserve human attention for conceptual integrity and alignment to the user's mental model. McKinney's line is the one to defend.
  7. Don't buy the canonical methodology yet. "Agentic engineering" names a real shift, but the field is too young for certified best practices. Adopt the posture — reliability, grounding, context discipline — and stay skeptical of anyone selling the framework.

§8 · GlossaryTerms used above, briefly

Context architecture
NN/G's framing of the design of an agent's context — instructions, memory, retrieval, tools — as an information-architecture problem. The same labeling, hierarchy, and findability discipline that organized websites, relocated to the prompt.
Context rot
The degradation in model output that sets in when context grows excessive or disorganized. A quality failure caused by too much, badly structured material — not a fixed model limitation but an architecture problem you own.
Agentic engineering
IBM's term for the discipline of designing and operating systems where AI agents plan and execute multi-step tasks autonomously. Foregrounds reliability, observability, and guardrails over single-turn answer quality.
Grounding
Anchoring an agent's outputs in authoritative domain or expert knowledge piped into its context, rather than relying on the base model alone. Spotify's "teacher" layer and LinkedIn's ranked retrieval are two implementations.
Re-sent context problem
The cost mechanism in multi-step agents: because accumulated context is re-transmitted to the model at every step, total token consumption grows roughly quadratically with task length rather than linearly.
Essential vs accidental complexity
Fred Brooks's distinction, revived by Wes McKinney for agents. Accidental complexity (boilerplate, glue, scaffolding) is what agents absorb well; essential complexity (conceptual design, integrity, mental-model alignment) is what stays human.
Conceptual integrity
Brooks's term for the coherence of a design under a unifying set of ideas. The property that does not parallelize — adding more agents (or more people) does not produce it — and the reason the "agent-month" is mythical.
